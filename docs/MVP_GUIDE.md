# MVP: запуск, демонстрация и проверки

## 1. Поднять отдельный стенд

Из `/Users/tvmag/programming/java` (на другом компьютере — из корня клона):

```sh
[ -f .env ] || cp .env.example .env
./demo/compose.sh up --build -d
./demo/compose.sh ps
./demo/compose.sh logs --tail=60 auth-service billing-service notification-service
./demo/compose.sh run --rm demo-tools seed
```

Нужны Docker Engine / Desktop и Compose v2. На первом запуске требуется сеть для образов и Maven/npm. Для локальной разработки дополнительно Java 21, Node 22+, Python 3 только при запуске demo/run.py на хосте. В Compose Python уже есть в demo-tools.

`demo/compose.sh` всегда использует проект `smartruble-mvp` (переопределяется `SMART_RUBLE_PROJECT`). Не смешивайте его с обычным `docker compose`: у другого project будут другие volumes. Порты 3000, 8080, 5433, 5434 должны быть свободны. При конфликте остановите свой старый стенд либо измените опубликованные порты; не удаляйте чужие контейнеры.

`seed` проходит через настоящий auth и gateway, создаёт четыре вымышленных контрагента с разными статусами и одно утверждённое распоряжение на 500 000 ₽. UUID пользователей выводятся для ручной привязки. Повторный seed сохраняет текущие бюджеты и платежи, но возвращает статусы демокомпаний к исходному сценарию.

Откройте http://localhost:3000. Пользователи создаются только при подключении `docker-compose.demo.yml`:

| Роль | Телефон | Возможности в демонстрации |
|---|---|---|
| Менеджер | +70000000001 | Контрагенты, свои распоряжения, сметы, привязки и заявки |
| Финансовый директор | +70000000002 | Проверка статусов, утверждение бюджетов, согласование, журнал событий |
| Подрядчик | +70000000003 | Распоряжения своей компании, создание платежных заявок |
| Сотрудник | +70000000004 | Просмотр назначенного распоряжения |

Пароль для всех четырёх: `Demo12345!`. Для разных ролей удобно открыть разные браузеры либо приватные окна. Токены хранятся в памяти вкладки, поэтому перезагрузка страницы требует повторного входа.

## 2. Что показать за 5–7 минут

1. Менеджер: откройте «Распоряжения» → демораспоряжение. Покажите смету: материалы 250 000, работы 150 000, оборудование 100 000 ₽. Объясните разницу между лимитом, резервом и фактическим расходом.
2. Подрядчик: создайте заявку на 10 000 ₽ проверенному поставщику «Материалы». Через несколько секунд статус станет «Оплачен», резерв уменьшится, потраченная сумма увеличится.
3. Создайте заявку на 60 000 ₽. Она останется на согласовании, а бюджет уже будет зарезервирован — параллельные заявки не смогут потратить эти деньги.
4. Финансовый директор: в «Согласованиях» откройте заявку, укажите основание и согласуйте. Покажите историю переходов и обновлённый остаток.
5. Подрядчик: попробуйте сумму выше доступного остатка — получите заблокированную заявку с объяснением. Заблокированные поставщики скрыты от подрядчика; их блокировку платежа можно показать из кабинета менеджера или через smoke.
6. Финансовый директор: откройте «Уведомления». События пришли через отдельный сервис и Kafka. Это журнал в приложении; push/email в MVP отсутствуют.
7. Покажите тест потери ответа банка и объясните, почему повтор использует тот же ID платежа.

Можно создать новое распоряжение: менеджер задаёт смету → финансовый директор утверждает → представитель выбранного подрядчика получает доступ. «Завершить работы» разрешено только после освобождения всех резервов.

## 3. Автоматическая сквозная проверка

```sh
./demo/compose.sh run --rm demo-tools smoke
```

Команда использует только демопользователей, создаёт отдельное распоряжение `[CHECK]`, отправляет запросы через gateway и ожидает реальный ответ consumer. Она проверяет:

- повтор Idempotency-Key возвращает тот же платёж; другая сумма с тем же ключом даёт 409;
- превышение бюджета и заблокированный получатель дают BLOCKED;
- подрядчик не может согласовать платёж (403), финансовый директор может;
- сотрудник не видит чужое распоряжение (404) и финансовый журнал (403);
- отклонение согласования освобождает резерв;
- отказ банка освобождает резерв, а потеря ответа после commit завершается повтором без второго списания;
- итог статьи: потрачено 64 000, резерв 0, доступно 36 000 ₽;
- уведомление о финальном платеже доходит через Kafka.

Ожидаемый результат: `SMOKE PASSED`. Скрипт действительно изменяет mock-баланс; повторные прогоны накапливают тестовые распоряжения и списания. Запускайте на отдельном стенде без параллельных ручных платежей: следующий банковский сбой предназначен именно этому тесту. После большого числа прогонов mock-баланс может закончиться — используйте новый Compose project со свободными портами или осознанно пересоздайте только демонстрационные volumes.

## 4. Сценарии сбоев вручную

Включить отказ для **следующего** запроса к банковскому mock:

```sh
./demo/compose.sh run --rm demo-tools bank-mode REJECT_ONCE
```

Создайте заявку ниже порога согласования. Ожидайте FAILED и возврат резерва. Потраченная сумма не меняется.

Потерять ответ после фиксации списания:

```sh
./demo/compose.sh run --rm demo-tools bank-mode TIMEOUT_AFTER_COMMIT
```

Создайте следующую заявку. Банк сохранит перевод, но задержит HTTP-ответ на 5 секунд; billing ждёт 2 секунды. Заявка остаётся PROCESSING с резервом. Повтор приходит с прежним UUID; банк возвращает сохранённый результат. Итог SUCCEEDED, одна запись перевода:

```sh
./demo/compose.sh run --rm demo-tools ledger
```

Недоступность Kafka:

```sh
./demo/compose.sh stop kafka
# Создайте платёж в интерфейсе; банк продолжает работать.
./demo/compose.sh exec billing-db psql -U billing -d billing_db -c "select count(*) as unpublished from payment_outbox where published_at is null;"
./demo/compose.sh start kafka
# После восстановления брокера счётчик уменьшится до 0, журнал пополнится.
```

Outbox не даёт атомарной транзакции между PostgreSQL и Kafka. Возможна повторная публикация после сбоя; consumer дедуплицирует по eventId. Не называйте это гарантией exactly-once всей системы.

Для DLT есть автоматический `DeliveryTest`: он отправляет повреждённое событие и читает его из `payment-events.DLT` после повторов. Дубликат корректного события сохраняет ровно одну строку. Ручной разбор и повторное проигрывание DLT пока не реализованы.

## 5. Тесты разработки

```sh
./scripts/test-all.sh
```

Или отдельно:

```sh
(cd auth-service && ./mvnw test)
(cd api-gateway && ./mvnw test)
(cd billing-service && ./mvnw test)
(cd abs-service && ./mvnw test)
(cd notification-service && ./mvnw test)
(cd web-client && npm ci && npm test && npm run build)
```

Billing и банк используют временную PostgreSQL через Testcontainers, notification дополнительно поднимает настоящий Kafka broker. Они не обращаются к вашим pgAdmin-базам. Auth использует тестовую H2. Шлюз проверяется с тестовыми upstream-серверами. JUnit-отчёты находятся в `<service>/target/surefire-reports`.

`PaymentWorkflowTest` проверяет два одновременных запроса по 60 000 при лимите 100 000: одна заявка резервируется, другая блокируется. Там же проверяются отказ, повтор, потеря ответа, восстановление после прерванного worker, смена реквизитов и запрет закрыть смету с резервом. Это проверки корректности; число тестов и их длительность не являются измерением пропускной способности системы.

Android: откройте `android-client` в Android Studio, установите SDK 35, выполните `./gradlew assembleDebug`, затем запустите эмулятор. Шаблон использует `10.0.2.2:8080`; в текущем окружении SDK отсутствует, полная сборка не подтверждена. На физическом телефоне loopback-порт Compose недоступен: для отдельного локального теста понадобится явная привязка gateway к LAN-интерфейсу и настройка адреса клиента.

## 6. Swagger и pgAdmin

http://localhost:8080/swagger-ui.html → auth-service → `/api/v1/auth/login`. Возьмите accessToken. В спецификации billing-service нажмите Authorize и вставьте JWT без префикса `Bearer`. Идентификатор и роли шлюз добавляет сам; подставлять X-User-* вручную не нужно. Для создания платежа Idempotency-Key — новый UUID на новую операцию, прежний UUID на повтор той же операции.

| Подключение pgAdmin | Host | Port | Maintenance DB | Username / Password |
|---|---|---|---|---|
| auth | localhost | 5433 | auth_db | auth / auth |
| billing | localhost | 5434 | billing_db | billing / billing |

Базы bank и notification доступны только в Docker-сети. Пример просмотра:

```sh
./demo/compose.sh exec notification-db psql -U notification -d notification_db -c "select status,count(*) from notifications group by status;"
```

Прямые SQL-запросы используйте для диагностики. Бизнес-операции выполняйте через API, чтобы не обходить резервирование и аудит.

## 7. Ограничения и развитие после MVP

- Это локальный single-tenant стенд. Нет tenant_id, изоляции разных компаний-заказчиков и промышленного управления доступом.
- Банковский mock списывает один начальный баланс и хранит переводы; полноценной бухгалтерской проводки с кредитованием счёта получателя нет.
- События обеспечивают журнал уведомлений; отчёт читается из billing, отдельной CQRS-проекции нет.
- Порог согласования фиксирован: 50 000 ₽. ML, скоринг по внешним данным, электронные подписи и смарт-контракты отсутствуют.
- Billing доверяет заголовкам внутреннего gateway. Перед внешним развёртыванием нужны TLS, изоляция сети, управление секретами, service-to-service authentication, резервные копии и нагрузочное тестирование. Демоучётки и общие пароли оставлять нельзя.
- Gateway проверяет подпись JWT локально: отзыв refresh или изменение роли не отзывают уже выданный access-token мгновенно. Для немедленного отзыва нужна отдельная политика.
- API списков платежей/распоряжений и сводки рассчитан на небольшой демонабор; нужны серверные фильтры и пагинация. В селекторе UI первые 200 контрагентов.
- Android остаётся шаблоном. Конкурсный сценарий реализован в веб-клиенте.

Перед выступлением прогоните smoke, восстановите NORMAL через bank-mode, проверьте звук/экран и отдельно подготовьте рассказ о проблеме заказчика, предполагаемой экономике и интервью с пользователями. Код сам по себе не доказывает спрос на продукт.

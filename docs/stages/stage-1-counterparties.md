## Шаг 3. Текущий пользователь в billing
Шлюз уже проверил JWT и передаёт `X-User-Id` (UUID) и `X-User-Roles` (`ROLE_MANAGER,ROLE_EMPLOYEE`).
Billing им доверяет (решение из обсуждения: внутренние порты закрыты).

Два варианта:

| | `@RequestHeader` в каждом методе контроллера | Spring Security + свой фильтр |
|---|---|---|
| Как | `@RequestHeader("X-User-Id") UUID userId` и ручная проверка ролей | фильтр читает заголовки и кладёт пользователя в `SecurityContext` |
| Проверка ролей | `if (!roles.contains(...)) throw ...` в каждом методе | `@PreAuthorize("hasAnyRole('MANAGER','ADMIN')")` |
| Текущий пользователь в сервисе | передавать параметром | `@AuthenticationPrincipal` в контроллере |
| Нет заголовка | у каждого метода своя обработка | единый ответ 401 |

**Рекомендация:** Spring Security, потому что модулей будет шесть и проверок ролей много. Понадобится:
- зависимость `spring-boot-starter-security`;
- `SecurityFilterChain`: без сессий, без CSRF; swagger и `actuator/health` открыты;
- свой `OncePerRequestFilter`: читает два заголовка и создаёт `Authentication` с ролями. Если заголовка нет,
  пользователь не аутентифицирован;
- `@EnableMethodSecurity`;
- маленький record вроде `CurrentUser(UUID id, Set<String> roles)` как principal.

Положить можно в модуль `config` или завести модуль `security`. Он нужен всем модулям, и это нормально:
зависимость от технического модуля циклов не создаёт.

Проверка: запрос без `X-User-Id` получает 401, запрос с ролью без нужных прав — 403.

## Шаг 4. Валидация: что нужно сейчас, а что подождёт

У валидации **четыре уровня**, и у каждого своя задача:

| Уровень | Что проверяет | Пример | Нужно сейчас? |
|---|---|---|---|
| **1. Формат запроса** (Bean Validation на DTO) | что поле есть и похоже на правду | `@NotBlank name`, `@Pattern("\\d{10}\|\\d{12}") inn`, `@Email`, `@Size` | **да** |
| **2. Бизнес-правила** (сервис) | что данные осмысленны вместе | КПП есть только у юрлица; ИНН юрлица из 10 цифр, ИП — из 12; причина обязательна для `BLOCKED` | **да** |
| **3. Уникальность и целостность** (сервис + БД) | что такого контрагента ещё нет | дубль ИНН+КПП → 409, а не 500 | **да** |
| **4. Контрольная сумма ИНН** | что в ИНН нет опечатки | `7707083893` верный, `7707083894` нет | **можно отложить** |

Почему уровни 1–3 нужны сейчас: без них ошибка пользователя упирается в `CHECK`-ограничение базы,
и клиент получает 500 «Внутренняя ошибка» вместо понятного «ИНН юрлица должен состоять из 10 цифр».
База — последняя линия обороны, а не способ общаться с пользователем.

Про контрольную сумму честно: это полезная защита от опечатки в реквизитах получателя денег, но это просто
алгоритм на 20 строк, и архитектуре он не учит. Позже проверка контрагента по ФНС (этап 6) поймает и
несуществующий ИНН. **Решение за вами:** сделать сейчас как разминку на unit-тесты или записать в бэклог.

Как превратить нарушение уникальности в 409: проверить `existsBy...` в сервисе перед сохранением (понятное сообщение)
**и** перехватить `DataIntegrityViolationException` в обработчике ошибок. Проверка в коде не защищает от
одновременного создания двух одинаковых контрагентов, а уникальный индекс в базе защищает.

## Шаг 5. Репозитории
Нужны не для каждой таблицы, а под сценарии:
- контрагенты: поиск по id; список с фильтром по статусу и поиском по названию с пагинацией (`Pageable`);
  проверка существования по ИНН+КПП;
- история статусов: список по контрагенту, новые сверху;
- участники: найти контрагента по `userId` (понадобится на этапе 2: «к какой компании относится этот подрядчик»).

Банковским счетам отдельный репозиторий, возможно, не нужен: они часть контрагента (см. ревью сущностей).

## Шаг 6. Сервис и бизнес-правила
Операции модуля:

| Операция | Правила |
|---|---|
| создать контрагента | уровни валидации 1–3; статус `NEW`; запись в историю (`old_status = NULL`, `source = MANUAL`) |
| изменить реквизиты | ИНН и тип менять нельзя (это уже другой контрагент); `updated_at` обновляется |
| получить карточку / список | подрядчик видит только **не** заблокированных контрагентов |
| добавить банковский счёт | первый счёт автоматически основной |
| сделать счёт основным | у прежнего основного снять флаг **в той же транзакции** |
| деактивировать счёт | не удалять; основной счёт деактивировать нельзя, пока не выбран другой |
| сменить статус проверки | причина обязательна для `BLOCKED` и `SUSPICIOUS`; новый статус ≠ текущего; запись в историю |
| привязать пользователя-подрядчика | только к контрагенту, который ещё не `BLOCKED`; один пользователь — одна компания |
| отвязать пользователя | |

## Шаг 7. REST API
Префикс `/api/v1/billing/counterparties`: шлюз уже маршрутизирует `/api/v1/billing/**` в billing.

| Метод и путь | Роли | Что делает |
|---|---|---|
| `POST /` | MANAGER, FINANCE_DIRECTOR, ADMIN | создать |
| `GET /?status=&search=&page=&size=` | все сотрудники; CONTRACTOR видит только незаблокированных | список |
| `GET /{id}` | то же | карточка с банковскими счетами |
| `PUT /{id}` | MANAGER, FINANCE_DIRECTOR, ADMIN | изменить реквизиты |
| `POST /{id}/bank-accounts` | MANAGER, FINANCE_DIRECTOR, ADMIN | добавить счёт |
| `PATCH /{id}/bank-accounts/{accountId}` | то же | сделать основным или деактивировать |
| `POST /{id}/status` | FINANCE_DIRECTOR, ADMIN | сменить статус проверки (`{status, reason}`) |
| `GET /{id}/status-history` | все сотрудники | история |
| `POST /{id}/members` / `DELETE /{id}/members/{userId}` | MANAGER, ADMIN | привязать или отвязать подрядчика |

Ответы — DTO, а не сущности. Ошибки — JSON в формате auth-service и шлюза
(`timestamp`, `status`, `error`, `message`, `path`, `fieldErrors`).
❓ Почему смена статуса — отдельный `POST /{id}/status`, а не поле в `PUT /{id}`?

## Шаг 8. Публичный API модуля
Интерфейс в **корневом** пакете `counterparties` плюс record, который он возвращает. Понадобится модулю
`workorders` на этапе 2, например: найти контрагента и узнать, можно ли с ним работать; найти компанию
пользователя-подрядчика. Можно сделать на этапе 2, когда появится реальный потребитель.

## Шаг 9. Тесты
Интеграционные (Testcontainers + MockMvc, заголовки `X-User-*` подставляются в запрос):
1. Менеджер создаёт юрлицо: 201, статус `NEW`, в истории одна запись.
2. Повторное создание с тем же ИНН+КПП: 409 с понятным сообщением.
3. ИП с КПП или юрлицо с 12-значным ИНН: 400 с `fieldErrors`.
4. Менеджер пытается заблокировать контрагента: 403.
5. Финансовый директор блокирует без причины: 400; с причиной: 200, запись в истории.
6. Второй основной счёт: прежний перестаёт быть основным.
7. Подрядчик не видит заблокированных контрагентов в списке и получает 404 на карточку заблокированного.
8. Запрос без `X-User-Id`: 401.
9. `ModularityTests` проходит.

Если делаете контрольную сумму ИНН — ещё unit-тесты на неё (верные и неверные ИНН обеих длин).
